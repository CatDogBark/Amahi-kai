# Changelog

All notable changes to Amahi-kai are documented here.

## [Unreleased]

## [1.4.4] — 2026-10-28

Transmission saves its downloads into shares, Uptime Kuma's ping monitors work, and Gitea keeps its repositories in a share folder.

### 🔒 Security & Fixes

- **Uptime Kuma's ping monitors work** (Apps) — A ping monitor was always down with "spawn EPERM": the `ping` in Uptime Kuma's image is marked to need raw sockets, which Amahi-kai doesn't give apps, and Linux then refuses to run it at all. An app's manifest can now name its ping (`ping: /usr/bin/ping`), and Amahi-kai mounts a copy of that same file, taken from the same image without the mark, in its place: it pings the way Docker lets any container, and the app still gets no raw sockets.
- **Transmission can save downloads into a share** (Apps) — Given a share with read and write, Transmission was denied writing into it: its image starts as root and then switches to the app's user with the groups the image itself lists, which dropped the `users` group Amahi-kai gives it. Now an app like that, given a share to write into, runs with `users` as its own group (`PGID`), so it writes where the share lets the `users` group write, and its files stay editable over SMB.
- **Gitea can keep its repositories in a share** (Apps) — Install now asks Gitea's shares, and a share folder given read and write can hold its repositories instead of the system disk: set **Repository Root Path** to that folder under `/shares` on Gitea's first page. The app catalog had it first; this is the copy that comes with Amahi-kai, and the wiki.
- **Transmission's and Uptime Kuma's first sign-in say what their first pages need** (Apps) — Transmission downloads to the system disk until its preferences point **Download to** at a share folder you gave it (under `/shares`) and its temporary folder is off, and its sign-in note now says so. Uptime Kuma's first page asks which database to use before the admin account (SQLite is the simple one).

### 🔧 Architecture & Code Quality

- **Browser tests give Chrome longer to start** — On CI's runners the first browser test, right after Chrome's cold start, sometimes timed out opening its page while every other test passed. The browser tests now allow 30 seconds a command and a minute for Chrome to start; one that hangs still fails.

## [1.4.3] — 2026-10-28

Apps can write into shares on a ZFS pool: Gitea, Transmission and bitTube install with read and write on one.

### 🔒 Security & Fixes

- **Apps can write into shares on a ZFS pool** (Apps) — An app given read and write on a share (Transmission, Gitea, bitTube) failed to install when the share was on a ZFS pool: Amahi-kai gives the app's folder a default ACL, so what the app makes there stays editable over SMB, and ZFS on Linux leaves ACLs off unless asked, so setting it failed with "Operation not supported". New pools have ACLs on (`acltype=posixacl`, kept beside each file with `xattr=sa`); on a pool made before, the share's dataset gets them the first time an app is given write access there. Files already on the pool keep their permissions.

## [1.4.2] — 2026-10-27

The root helper's source is split by area, for working on it; nothing changes in what Amahi-kai does.

### 🔧 Architecture & Code Quality

- **The root helper's source is split by area** — `libexec/amahi-helper` had grown to 7,800 lines in one file. Its code now sits in nine parts in `libexec/amahi-helper.d/` (core, sharing, disks, ZFS pools, Greyhole, DNS, network, apps, system), each area's operations beside their code, moved unchanged: every setting, operation and method is byte for byte what it was. It's still installed as one file: `bin/amahi-join-helper` puts the parts in place, and the installer self-tests that file before it replaces the helper, as before, so the helper that runs as root still loads nothing but Ruby's standard library. Nothing changes in what it does.
- **Brakeman reads the root helper now** — CI's security scanner only reads `.rb` files, so it never saw the helper as one file without an extension. It does now, and the three lines it flags, there all along, are recorded in `config/brakeman.ignore` with why each is safe: the HTTPS apps' health check (a TLS handshake with the app on the server itself), the app catalog's `git` (an argument list, no shell), and netplan's settings copied in memory.

## [1.4.1] — 2026-10-27

The Apps page puts your apps first, each saying whether it's running, and gives each app a page of its own for everything else.

### 🚀 Major Features

- **The Apps page, laid out again** (Apps) — Your apps come first, as cards that say in a word whether each is **Running**, **Stopped**, **Installing…** or **Needs attention**, with **Open** (or **Start**) and **Manage**; below them, **Add apps** lists the catalog's other apps by category, with **Install**. Before, one table mixed both, the state of an app was only told by its buttons, and each app's sign-in and passwords sat on a row of their own that read like another app. **Manage** opens the app's own page, with everything else: how to sign in and the passwords Amahi-kai made for it, hidden until **Show** (**Copy** copies one without showing it), its address, ports and version (**Update**, **Undo update**), its shares and storage (**Change**), and **Stop** and **Uninstall**. The Installed tab is gone; its old address opens the Apps page.

### 🔧 Architecture & Code Quality

- **Lucide's licence ships with its icons** — The icons on Amahi-kai's pages are Lucide's (ISC licence; the ones derived from Feather, MIT), and their licence notice now sits beside them (`app/assets/images/icons/LICENSE-lucide`), as both licences ask.

## [1.4.0] — 2026-10-27

Devices keep their names wherever DHCP puts them and apps reach them by name, so a camera viewer needs no fixed addresses; Install asks for shares only for apps that work with files in them; and bitStream brings the home's cameras to the browser, Android and the KDE desktop.

### 🚀 Major Features

- **Devices can be named without fixing their address** (Network → Devices) — **Name** on a device gives it a name of your own that follows it wherever DHCP puts it, answering in DNS at once (`carport-cam`, and `carport-cam.home.arpa`): reach it by its name and let its address change. **Unfix** keeps the device's name now, and **Forget** drops it. Devices whose own names have an underscore (Wyze cameras ask for `WYZE_CAKP2JFUS-…`) answer with a hyphen in its place instead of not at all. A device can't be called `ignore` or `infinite`: dnsmasq read those as orders, and a device named `ignore` got no address.
- **Apps reach devices by their names** (Apps) — While the NAS's DNS is on, apps ask it, so an app reaches a device by its name on Network → Devices (a camera viewer at `carport-cam`, say), and apps get the NAS's blocklists too; before, they asked the NAS's upstream servers, which know none of the LAN's names. Turning DNS on or off makes the apps' containers again in the background, keeping their data, and so does this update, once, on a NAS whose DNS is on: each app restarts for a minute or so after it.
- **bitStream joins the app catalog** (Apps) — The home's cameras, live: in the browser, on Android (its app downloads from bitStream itself and updates itself from there) and in a KDE Plasma widget, with switches for Wyze floodlights. Cameras are added by their names on Network → Devices. One password, made at install, for its pages, its streams and its API.

### 🔒 Security & Fixes

- **Install asks for shares only for apps that use them** (Apps) — Every app's Install asked which shares to give it, Vaultwarden, Gitea and Uptime Kuma too, which never read a file in one: an app given shares it has no use for only gets files it shouldn't see. Now an app that works with files in shares says so in the catalog (`shares: true`, or `writes_shares`), and only those ask: Jellyfin, PiGallery2, Transmission and bitTube. The others install without the dialog (bitShare's asks only for its ZFS pool), and their rows have no shares line, unless they were given shares before. Vaultwarden's row has a link of its own to give it its new address after the NAS is renamed in Tailscale (it was the shares' Change).

## [1.3.1] — 2026-10-27

Tailscale's Connect works in Firefox and with pop-up blockers: its sign-in is a link to click, and the page waits for it.

### 🔒 Security & Fixes

- **Tailscale's Connect works in Firefox, and with pop-up blockers** (Network → Remote Access) — Connect asked the NAS for Tailscale's sign-in page, then tried to open it in a new tab seconds later, which Firefox blocks as a pop-up; the page then reloaded five seconds on and showed Connect again, so it looked as if Connect had failed. The page opens nothing itself now: it shows **Sign in to Tailscale to finish**, a link to the sign-in page, waits while you sign in (in that tab, or on any device), and shows the NAS connected once it is. The install window does the same.

## [1.3.0] — 2026-10-27

Vaultwarden works now, reached only from devices on your Tailscale network, over HTTPS with Tailscale's certificate, and given its admin token hashed; CI jobs have time limits.

### 🔒 Security & Fixes

- **Vaultwarden works, reached only through Tailscale over HTTPS** (Apps) — Vaultwarden couldn't be used: browsers won't run its web vault over plain HTTP, and the Bitwarden apps now refuse a server that isn't HTTPS, so only its admin page answered. An app like it is now reached only from devices on your Tailscale network, at `https://<the server's name on your tailnet>:<its port>`, with Tailscale's certificate. It's never on the LAN or the internet: its port is open on the server itself only, and it isn't announced on the LAN. It installs once the server's Tailscale is connected with MagicDNS and HTTPS Certificates on (switches in Tailscale's admin console, under DNS); until then the Apps page says what's missing, and Network → Remote Access shows whether HTTPS certificates are on. Vaultwarden itself comes to this with the catalog's next change.
- **An app's admin token can be given to it hashed** (Apps) — Vaultwarden warned that its admin token was given to it as plain text. An app can now be given an Argon2id hash of a password Amahi-kai makes, while its row on the Apps page still shows the password itself to sign in with.

### 🔧 Architecture & Code Quality

- **Apps reached only through Tailscale, and hashed secrets** (catalog format 5) — A manifest that says `requires: 5` can set `access: tailscale`: its ports are published on the server itself only, its web port is served on the tailnet over HTTPS by `tailscale serve`, and `{{tailscale_url}}` in its environment is that address. A secret can say `hash: argon2`, and the container gets an Argon2id hash of it (Ubuntu's `argon2` is installed the first time one is needed). Servers on an older Amahi-kai list such an app as needing a newer one.
- **CI jobs have time limits** — A step that hung ran until GitHub's 6-hour limit: an Ubuntu mirror that stopped answering held three CI jobs on `apt-get` until they were cancelled by hand. CI's jobs now stop after 20 minutes, the release after 15 and the website's deploy after 10, so a hang fails and can be run again.
- **`config.ru` and the `Rakefile` as Rails 8 writes them** — They did the same job in Rails 3's words (`File.expand_path(..., __FILE__)`, a stray shebang, the application's class by name); both now use `require_relative` and `Rails.application`. Nothing changes in how the server starts or the tasks run.

## [1.2.0] — 2026-10-26

Apps can be given only some folders of a share rather than all of it, and services with nothing to do (Greyhole without drives, SMART monitoring without a drive that has SMART) no longer fail at every boot.

### 🔒 Security & Fixes

- **Apps can be given only some folders of a share** (Apps → Shares) — An app was given whole shares: Jellyfin given Vault for its movies could read everything else in Vault too, and Transmission given it to download into could change all of it. A share can give only some of its folders now, picked in a browser of the share's folders, each read only or read and write; they appear in the app where they are in the share (`/shares/Vault/media/Pictures`), and the rest of the share is out of the app's reach. Amahi-kai mounts each folder itself, checked to be a real folder reached through no link, and again before Docker starts the apps after a restart, so an app that writes in a share can't swap a folder for a link to elsewhere on the server. A folder renamed or deleted keeps its app from starting until it's given its folders again, and the app's row says which.
- **Services with nothing to do don't fail at every boot** — Greyhole installed with no drive in its pool, and SMART monitoring (smartd) on a server whose drives have no SMART data (virtual disks, in a virtual machine), started anyway, failed, and were listed as failed at every boot; smartd failed at every System Update too. Each runs now, and at boot, only while it has work: Greyhole once its pool has a drive (it starts with the first one and stops with the last), smartd while a drive has SMART data (the storage check starts it within 15 minutes of one being connected). This update switches off one that has none. Stop on Disks → Greyhole Pool now keeps Greyhole off after a restart too.
- **Uninstalling Greyhole leaves no failed service behind** (Disks → Greyhole Pool) — After Uninstall, systemd went on listing `greyhole.service` as failed until the next restart. Uninstall clears it now.

## [1.1.0] — 2026-10-26

PiGallery2, a photo gallery, comes to the app catalog with this release; every app says how to sign in the first time; and the dashboard shows your storage pools.

### 🔒 Security & Fixes

- **Each app says how to sign in the first time** (Apps) — The Apps page gave no word on how to get into an app once it was installed: the password Amahi-kai made for PiGallery2 sat in a folded list, and nothing said its user is admin, or that Jellyfin, Gitea, Uptime Kuma and bitTube have you make the first account on their own first page. Every app in the catalog now says how, under the installed app on the Apps page (above the passwords Amahi-kai made for it) and when its install finishes.
- **The dashboard shows your storage pools** — The System card listed the drives `df` lists, which leaves out a ZFS pool: a NAS whose storage is a ZFS pool showed none of it, while a Greyhole pool's drives were listed one by one as well as on the pool's own card. A Storage card has a row for each pool now: a ZFS pool's layout, drives, health and usable space after parity, as Disks → ZFS Pools gives them (from the storage check, every 15 minutes and after any change to a pool), and the Greyhole pool's space, copies and pending work. The System card keeps the system disk and the drives that are storage on their own.
- **Disks → Devices says what comes after formatting** — A drive formatted there (Initialize or Format) is left unmounted, and Greyhole's pool and shares only take mounted drives, but the page said only "Successfully formatted", and beside the drive, when ZFS was installed, only how to keep it for a ZFS pool. It says to mount it for shares or Greyhole's pool now, and the hint beside the drive gives both ways.

### 🔧 Architecture & Code Quality

- **Apps can be set up the way they name their settings** (catalog format 4) — A manifest that says `requires: 4` can spell its environment names as the app does (PiGallery2's `Media-folder`), and put a generated secret inside a setting (`{{secret:NAME}}`), such as an admin password inside a list of users, so the app never starts with a default password. It's what PiGallery2, the photo gallery now in the catalog, needs. Servers on an older Amahi-kai list such an app as needing a newer one.

## [1.0.0] — 2026-10-25

Amahi-kai 1.0 is a home server for Ubuntu 24.04, run from your browser, and the first release meant for other people to install. On a dedicated machine or virtual machine it gives you:

- **File shares** for every computer in the house (Samba), with per-user access, a Trash, a web file browser and search.
- **Storage** on plain drives pooled by Greyhole, with copies of a share's files on different drives, or on **ZFS pools** (mirrors and RAIDZ) with hourly and daily snapshots, roll-back, scrubs and drive health.
- **Apps** from Amahi-kai's own catalog in a click: Jellyfin, Vaultwarden (its web vault needs HTTPS, which comes later), Gitea, Uptime Kuma, Transmission, bitTube, and bitShare, which is early. Each runs on its own port, reachable from your LAN and Tailscale only, and an update copies the app's data first and goes back by itself if the new version fails.
- **Your network**, if you want it: the NAS as its DNS server (private, checked with DNSSEC, with ad and tracker blocking), its DHCP server, and its router, letting nothing in from the internet but the ports you choose. The NAS's own address is set from the page, with a guard against locking yourself out.
- **Remote access** through Tailscale or a Cloudflare Tunnel, a **security audit** that fixes what it finds, and **System Update** from published releases on a channel you pick, going back by itself when a step fails.

Every root action goes through one helper that checks and logs it, and the code it runs belongs to root. 1.0 doesn't yet back up the NAS's own settings ([what to keep copies of](https://amahi-kai.com/wiki/getting-started#what-amahi-kai-doesnt-back-up)), serve HTTPS on the LAN, or sign its updates; those come after 1.0.

Coming from 0.10.2, what changes is the 1.0 review's: a full pass over the code (the router's rules, the updater and installer, storage, apps, the rest of networking and the web app) and over the docs, with these fixes.

### 🔒 Security & Fixes

- **The internet side stays shut while router mode saves** (Network → Internet) — Every save on the Network pages rewrote router mode's rules by taking them all out and putting them back, the internet side's deny among the last. For a few seconds the NAS's SSH, web page and Samba answered from the internet, and a failure partway left them that way. Now the deny goes in first, before the internet port gets its address, and stays; a save takes out only the rules it no longer needs. Turning router mode off takes the internet port off the network before its deny goes.
- **A MariaDB update no longer stops the web page** — The web page's service required MariaDB's, and MariaDB's package update stops MariaDB, so the web page stopped with it until the next reboot; with automatic security updates on, nobody had to be there for it. An update started from System Dependencies could also be cut off partway, leaving the package system broken. The web page now only wants MariaDB, and package updates run as a job of their own that nothing in the web page can interrupt.
- **This NAS won't change the tunnel's or Tailscale's port from over them** (Network → Devices) — The guard against a wrong address only watches a change made through the port being changed. Through the Cloudflare Tunnel or Tailscale, a wrong address on the port they run over was applied at once and cut the way back in for good. That port is changed from the LAN now, where the guard watches.
- **DNS and DHCP stay on the LAN in router mode** (Network → DNS) — Picking the router's internet port as the one DNS answers on moved Unbound, the IPv6 announcement and DHCP there before router mode refused it, cutting the house's DNS and DHCP. The internet port is left out of the list, and refused.
- **DHCP needs the NAS's own address to be fixed** (Network → DHCP) — DHCP could be turned on while the NAS took its own address from DHCP, which worked until its lease ran out; then the house lost DHCP and DNS. DHCP now asks for a fixed address first (This NAS). Turning router mode off while DHCP stays on keeps the fixed address router mode gave the LAN.
- **Router mode that fails to go on isn't left half on** (Network → Internet) — DHCP started handing out the NAS as the way to the internet before router mode's rules were in place, so a failure there left devices with a router that didn't route, and the page still said router mode was on. The rules go in first now, and a failure leaves the mode as it was.
- **Router mode keeps what works when something is missing** — When netplan refused a save's new file for the internet port, the file that worked was deleted, so the next restart left the house offline; it's put back now. If the internet port itself went missing (a USB adapter resetting, a renamed port), the next save turned router mode off and dropped the house's NAT; the rules now stay until the port is back. And turning router mode off puts the kernel's forwarding back as it was, which Docker's apps need.
- **No made-up drives** (Disks → Devices) — When lsblk didn't answer, the drive list showed built-in sample drives, and acting on one acted on whatever real drive had its name. The page now says lsblk didn't answer.
- **An update that stops partway goes back, or is finished by the next one** (System Update) — Once the new code was checked out, some ways of stopping (a lookup failing in the update's second half, a signal, the job's time limit) left it on disk without its gems, database changes, page files or helper, while the log said nothing had changed; every later update then called the NAS up to date, and it broke at the next restart. Now any stop after that point puts the version that ran back, and an update cut off where even that can't happen (a power cut) is finished by the next update. The second half no longer asks GitHub for the version again, and keeps the update lock throughout.
- **Going back puts the previous version's settings back too** — A rolled-back update left the new version's Samba configuration and network rules (the router's among them) in place; the previous version writes its own again. A Repair that failed while rebuilding the page's files puts the old ones back instead of leaving the web page without them.
- **A helper that fails its self-test is never installed** — The root helper was copied into place before its self-test, so a broken one stayed, every change failed, and the update still said it succeeded. The new helper is now tested beside the old one and replaces it only if it passes, and an update whose helper doesn't install goes back.
- **The installer won't run Amahi-kai as an account people sign in with** — If an account named `amahi` already existed (the owner's own login, named when Ubuntu was installed, or a cloud image's with sudo), the installer ran the web app as it, giving the app everything that account has. It now stops and says why, unless the account is a system account like the one it makes.
- **The one-line installer leaves an installed NAS on its version** — Run again on an installed NAS, it moved the code to main's newest commit, without System Update's backup and rollback, and took a NAS on the development channel backwards. It now runs that NAS's own installer on the version installed; new versions come through System Update.
- **The installer's secrets stay private while it writes them** — The configuration file was readable by everyone for the moment its secrets went in, and the first password was written into a folder the app's account already owned. Both are written while only root can reach them.
- **The security audit's fixes don't shut SSH out** (Network → Security) — Turning the firewall on let SSH in on port 22 only, shutting out an SSH server on another port; it now lets SSH in wherever it listens. Turning root's SSH login off is refused while no other account can log in over SSH.
- **Package updates never remove a package** (Settings → System Dependencies) — apt is told to stop instead.
- **System Update finds the newest release when GitHub's list doesn't answer** — GitHub allows 60 lookups an hour from one address, which homes behind a provider's shared address use up together; the releases and candidates channels then read the repository's tags.
- **A Repair asked for during an update doesn't carry over** — It turned the next update into a repair that installed nothing.
- **A pool that isn't open shows, with Import** (Disks → ZFS Pools) — A pool on the drives that the NAS hadn't opened (after Amahi-kai was installed again, or when its drives came too late at boot) vanished from the page, and its drives were offered as free, with Erase and a new pool. It gets a card of its own now, with **Import**, which mounts it only if Amahi-kai made it. Its drives are kept for it, and erasing one asks for the pool's name.
- **A new pool can't take an offline pool's name** (Disks → ZFS Pools) — The page even suggested it, and the offline pool then vanished, its drives offered for Erase. The name box checks the name in the browser again, too: its pattern was one today's browsers refuse, so they skipped it.
- **Mount as Share, and the setup wizard's NTFS, FAT and exFAT drives, work** (Disks → Devices) — They made a share at the drive's own folder, which Samba's config check refused: Devices gave an error page, and after the wizard every later change to Samba's settings was refused too, noted only in the log. Such a drive is shared as it is now, its files where they were, and FAT and exFAT drives are mounted so the users group can write to them. A Samba config that's refused is shown on Shares.
- **A drive that comes back unmounted goes back to its place** (Disks → Devices) — Mount put it at the next free slot, so Greyhole still saw its own drive as missing. It goes where its fstab line says now, and the page says where it belongs, Format's warning included.
- **A page left open acts on the drive it showed** (Disks → Devices, ZFS Pools, setup wizard) — The drive buttons named drives by the kernel's name (`/dev/sdb`), which can belong to another drive after a restart or a swap. They name the drive by its model and serial now (its `/dev/disk/by-id` link), and a drive that's gone is refused.
- **Pools Amahi-kai didn't make are left alone** (Disks → ZFS Pools) — A server that runs from ZFS has its own pools (bpool, rpool), which the page could take offline, delete or roll back, and the hourly job took snapshots of them. They're shown with nothing that changes them now, and shares and apps can't go on them. Deleting a pool wipes a whole disk only when all of the disk was the pool's.
- **ZFS Pools says what's on a free drive** — A drive with files on it said only Free, and share storage that wasn't mounted just then counted as free too.
- **Unmount keeps a drive with a share on it** (Disks → Devices) — Unmounted, its shares served an empty folder, and the next drive mounted in its place took them over.
- **Devices says what comes before unmounting** — Unmount was offered on Greyhole's drives and on drives with a share on them, asked to be confirmed, then refused. The page now says to take the drive out of the Greyhole pool, or delete the share, first. Error messages stay until they're closed, so a refusal's reason can be read.
- **Taking the last drive out of the Greyhole pool stops Greyhole** — It was restarted, which fails with no drive, and showed as failed.
- **Snapshots are named in UTC** — In the hour the clocks go back, an hourly snapshot's name repeated and the job failed.
- **New fstab lines are checked** — Mount's and the swap file's lines could run into the last line when the file didn't end in a line break, and weren't checked like the other fstab changes. They are now, before the drive is mounted.
- **Sleeping drives stay asleep** — Reading the drives' temperatures woke spun-down drives (Disks now says Asleep), and so did the health check every 15 minutes once a pool had been taken offline. Only the ZFS Pools page reads the drives for pools that aren't open.
- **ZFS's memory cap holds on big servers** — ZFS keeps at least a 32nd of the memory for its cache and refused the 2 GB cap on a server with more than 64 GB, while the install said it was set. The cap there is just above ZFS's own, and the install reports the one ZFS uses.
- **Preview leaves btrfs drives as they are, and says when it stopped counting** (Disks → Devices) — A read-only preview of a btrfs drive could still replay its log onto it, and a preview cut short by its time limit looked complete.
- **The Greyhole trash checks its own folder** — Restoring or deleting a file from the Trash now refuses a drive's trash folder that is a link.
- **An app is given a share's folder only, never what a link points to** (Apps) — The share root belonged to the web app's account, and the helper didn't check a share's folder for links before mounting it into an app, so that account could have handed an app any folder on the server. The share root is root's now (System Update changes it), a share whose folder is reached through a link is refused when the app is installed and again just before its container is made, and remaking apps for a Greyhole pool change checks their shares the same way.
- **A reinstall that fails leaves the app as it was** (Apps) — The old container was removed before the new one was made, so a failed create left the app with none, and Install again then moved it to a newer version with no copy of its data. The new container is made beside the old one and swapped in; a failure starts the old one again. Each container's definition is kept, so a reinstall, an Undo and a roll-back rebuild it as it was, instead of running the old version with the newer catalog's settings; data kept at uninstall comes back on the version it's from.
- **Updates and Undo don't strand an app** (Apps) — A copy that failed before an update left the app stopped; it starts again on the version it ran. Undo downloads the old version again before it touches the data, and changes nothing if it can't. An HTTPS-only app (Vaultwarden) is checked with a TLS handshake after an update, instead of being rolled back for not answering plain HTTP. A catalog version older than the one an app runs isn't offered as an update, and the helper refuses it.
- **App jobs run on their own, one at a time per app** (Apps) — An install, update, undo or uninstall ran inside the web page's own service, so a restart of it cut the job off and left the app on Installing for good. Each job is a system job of its own now; the Apps page settles a row its job left behind; and while one job runs for an app, another, its Start and Stop, and the Greyhole pool's remake wait for it. Two apps' jobs no longer lose each other's port and storage records.
- **Apps the catalog dropped can still be stopped and uninstalled** (Apps) — Every app operation read the app's current catalog entry, so one the catalog dropped or moved on was stuck until System Update. Uninstall also waits for Docker: run while Docker was stopped, it left the container, which came back unlisted.
- **App ports stay shut at boot and follow the network** — Docker started the apps, ports and all, before their firewall rules were in; the rules are in place before Docker starts now, and are swapped in in one step instead of rule by rule. They're rebuilt when router mode goes on or off and when This NAS's address changes, so devices on a new subnet reach the apps and an old one stops being let in.
- **Apps get limits and stricter definitions** — Containers keep at most 30 MB of logs, run at most 2,048 processes, and can't use raw sockets or make device files. A definition's folder paths must be plain names, away from where shares go, one folder a path; `DOCKER_MODS`, which has an image download more code at start, is refused. Shares are saved on an app's record only once the helper has given them, and the Greyhole pool's remake reports the shares each app has now. Undo update says when it also takes the ZFS pool's later snapshots of the app's data with it.
- **Router mode's saves leave the network files alone when nothing in them changed** (Network → Internet) — Every save on the Network pages applied the netplan files again, and an apply sets up every port again: the internet port asked the provider for its lease again, and the NAS's own IPv6 address for DNS went while the NAS kept announcing it. A save applies them now only when one changed, and that address is put back after every apply.
- **Turning router mode off doesn't bring back old network files** — A LAN file changed by hand while the NAS was the router was left as it was, but its copy from before stayed beside it; a later router session kept that copy, and turning that one off put it back, undoing the hand change and everything since. The copy goes when the file is left, and a copy left from before is made again.
- **Port forwards and LAN only say when the router's rules didn't follow** (Network → Internet, Devices) — Adding or removing a forward, or turning a device's LAN only on or off, said it was done even when the router's rules weren't rewritten: the port stayed as it was, or the device did, until some later save. The page says so now, and Network → Internet shows the rules as behind until a save puts them in place.
- **Devices can't name themselves wpad, isatap or localhost in the NAS's DNS** — A device's name comes from the device when it asks DHCP for an address, and browsers look for their proxy settings at wpad, Windows for an IPv6 tunnel at isatap. Those names are skipped.
- **Router mode's lockout check looks at the port you came in on** (Network → Internet) — It refused to make the port you're connected through the internet side by comparing your browser's address with that port's network, which a browser on a network routed to the port passes, and one on the LAN port with an address in that network doesn't. It goes by the port the request arrived on now, as This NAS does.
- **This NAS keeps a /24 on the port DHCP serves** (Network → Devices) — DHCP's range and the fixed devices' addresses are the last part of an address on a /24, so another network size there is refused while DHCP is on.
- **The internet side drops service discovery** (Network → Internet) — UFW lets mDNS and SSDP in ahead of all its other rules, the internet side's deny among them, so the NAS's discovery services could be asked from the provider's network. Router mode drops both on the internet port, over IPv4 and IPv6.
- **Network changes take turns** — Two at once (This NAS's address kept and put back at the same moment, or two saves of router mode) could interleave their steps; each waits for the one before it now.
- **Tighter checks on network settings** — The root helper refuses the interface names `.` and `..`, a radvd config that doesn't say the NAS is no router, a dnsmasq config that would answer DNS, and Unbound access lists that add up to a large part of the internet.
- **Sign-in limits hold whatever the path** — The limits on sign-in attempts matched the form's exact path, so another spelling of it (`/user_sessions.json`) went around them, and the hourly ban counted successful sign-ins too, shutting out someone who signs in often. They're counted at the sign-in itself now, and only wrong passwords count toward the ban.
- **Remember me does what it says** — Every sign-in lasted seven days, ticked or not. Unticked, a sign-in ends when the browser closes or after 12 hours unused; ticked, after 7 days unused. Any sign-in ends 30 days after it was made.
- **Signing out ends the sign-in everywhere** — The sign-in lives in the browser's cookie, and signing out cleared only that browser's copy; a copy kept elsewhere went on working. Signing out now ends every sign-in of the account. Through the Cloudflare Tunnel the cookie is sent over HTTPS only.
- **Amahi-kai answers to its names as they are now** — The names it answers to were read when it started, so after a rename, and for its name in the NAS's DNS (`nas.home.arpa`) and the DNS aliases pointing at it, browsers got the "doesn't answer to the name" page. Those names work at once now.
- **Names with emoji save** — The database connection used MariaDB's three-byte utf8, which can't hold emoji: a user's name with one wasn't saved, and a file named with one stayed out of the search. The database and its tables move to utf8mb4 with this update.
- **The setup wizard won't take the installer's password back** — Typed again as the new one, it was accepted, and the security audit then took the password as changed.
- **Security fixes say why they didn't work** (Network → Security) — A fix's reason was kept in one place for every request, so it could be another one's, and Samba's fix gave none.
- **Jobs show the security updates off when they are** (Settings → Jobs, Dashboard) — They showed as daily and OK.
- **Share links work with spaces and subfolders** (Shares, Search) — A space became a + and a subfolder's slashes were encoded, so the links opened nothing.
- **Phones get the phone layout** — The main pages had no viewport setting, so a phone showed the desktop page shrunk, and the header's phone menu never appeared.
- **The audit's Change Password opens Users**, where passwords change, not Settings.
- **System Status shows the LAN address** — It showed whichever address the system listed first, which can be the public one while the NAS is the router.
- **Share sizes and the Delete button put text into the page as text** (Shares) — They put it in as HTML: du's messages, which name files, and the button's own text, which names the share.
- **Deleting a user deletes its share permissions** — They were left behind; the ones left by users deleted before go with this update.
- **New share names are ones Samba can use** — A share could be named `global` or `homes`, Samba's own sections, or with punctuation Samba and Greyhole don't take. New names are letters, digits, spaces, hyphens and underscores; shares named before keep theirs.
- **A share's Samba settings are saved only once Samba takes them** — An older way in to the same action saved them unchecked; it's gone.
- **A share's size counts the share** — The count followed links anywhere, other filesystems included. It stays on the share's own filesystem now (a pooled share's Greyhole links still count), and stops after 30 seconds.
- **Times are in your time zone** — The dashboard's date, file dates, Jobs, the pools' next scrub and snapshots, Servers, the apps' Undo, shares' and users' dates and the tunnel's start were the server's clock, which is UTC on most NASes: the dashboard's date turned over at 2 pm in Hawaii. The browser writes them in its own time zone now.
- **The setup wizard names a ZFS pool's drives** — Its storage step leaves out drives that hold a ZFS pool, so it can't format one, but when they were the only other drives it said there were none besides the system's. It names the pool now, and says to import it on Disks → ZFS Pools once setup is done.

### 📚 Docs

- **The docs describe 1.0 as it is** — The README and the website list networking and ZFS pools, and the apps with bitShare marked early and Vaultwarden's HTTPS note, and ask for a dedicated machine with a system disk of 32 GB or more (the dashboard warns below 10 GB free, so 10 GB set it off on the first day). The wiki says what Amahi-kai doesn't back up, explains the three roles (Admin, User, Guest), gives the steps for a ZFS pool after installing again, says the drive-failure paths were tried on virtual drives, and uses today's page names. It no longer says apps open through the tunnel (they're LAN and Tailscale only), that Samba is bound to the LAN interface (it listens everywhere behind its allow list), or that each user has a private home share. There's one CONTRIBUTING now, NOTICE is current, and the privilege model describes the fetched app catalog and names the unsigned catalog and updates as known gaps.

The installer's last lines say Amahi-kai doesn't back the server up. Settings → Servers, System Status and the dashboard use today's page names; the dashboard's Names button opens Network → DNS.

### 🔧 Architecture & Code Quality

## [0.10.0] — 2026-10-24

The NAS can be the house's router: a second network interface takes the provider's connection, every device reaches the internet through the NAS, and the old router becomes an access point. With it comes the shield (every device uses the NAS's DNS, LAN only per device, forged packets dropped, nothing from the internet gets in but the ports you let in), the NAS's own address set from the page with a guard against locking yourself out, and the Network tab split into Devices, DNS, DHCP and Internet. All of it was built and tried on an isolated test network, firewall on and after a reboot ([the list](docs/testing/networking.md)); the house itself, with a real provider, is still to try. A server that doesn't turn any of it on only gets the fixes below.

### 🚀 Major Features

- **The Network tab, split** — One page held DNS, DHCP, the router, blocking, IPv6 and port forwards. Now **Devices** (the devices the NAS gave addresses to, and their fixed addresses, in one list: Leases and Hosts folded together, with *Fix this address* on any device seen), **DNS** (the provider, blocking and its lists, the allowlist, the names: DNS Aliases folded in), **DHCP** and **Internet** (the router, its forwards, IPv6), beside Remote Access and Security. The one four-way mode became a switch on each page, with the dependencies kept: DHCP needs DNS on, the router needs DHCP on, and turning one off turns off what builds on it. The old addresses open the new pages.
- **Router mode** (Network → Internet) — A fourth mode: the NAS is the way to the internet. A second network interface takes the provider's connection, your devices reach the internet through the NAS, and your old router becomes an access point. Nothing from the internet reaches the NAS or your devices except the ports you let in, on the page's new card (a port, a protocol, the device, its port). It needs the firewall on, and it refuses to turn the interface you're connected through into the internet side. The LAN interface's own network settings are adjusted for you (an address from the old router kept as a fixed one, its route stepped behind the internet's) and put back when you leave the mode. The page says the way back.
  - **Every device uses the NAS's DNS** (on by default in router mode): a device that asks a DNS server of its own choosing (Roku, Google's, some TVs) gets the NAS's answer anyway, its own encrypted DNS doesn't get out, and the known encrypted-DNS services are blocked by name through Blocking. Tailscale's port is let in on the internet side when Tailscale is installed, so its connections stay direct.
  - **LAN only** (Network → Devices): a device with a fixed address can be kept off the internet with one click. It still reaches the shares, DNS and everything on the LAN; nothing beyond. For the TV, the camera, the toy that has no business out there.
  - **Forged packets dropped, and the knocking counted** (Network → Internet): a packet from the internet claiming an address inside your network is dropped by the kernel before anything sees it, and the page counts them, beside the count of connection attempts at the NAS from the internet that the firewall dropped. The NAS no longer answers pings from the internet (the firewall's own rules let them through), and a LAN-only device can't ping out either. ICMP redirects are neither taken nor sent on the internet side (a redirect could move the NAS's routes), and packets with an impossible source arriving there are logged by the kernel, for a WAN log later.
  - **Security updates for a router** (Network → Internet): a NAS that is the house's router faces the internet, so the page says whether Ubuntu's security updates install by themselves and points at the switch (Settings → System Dependencies, which now says what it is: security fixes only, from Ubuntu's security channel, never new versions of anything); the security audit warns while the NAS is the router without them.
- **This NAS** (Network → Devices) — The NAS's own address on each network port, set from the page: from the network (your router's DHCP), or fixed, with its network size, router and DNS servers. Nothing needed the terminal before. Changing the address you're connected through moves the page with it: the change is kept only once the NAS answers at the new address, and otherwise the NAS goes back to the old one by itself after 90 seconds, so a wrong address can't lock you out. The shares, DNS, DHCP and the router follow the new address. The internet side in router mode is the Internet page's. Each port also says what it is (the card's model, or a virtual port in a VM), whether a cable is in and at what speed, and its MAC; *Name* gives a port a name of your own, shown wherever it comes up, and *Find port* blinks a real port's light to find its socket.
- **Lists for the devices you have** (Network → DNS, Blocking) — HaGeZi's per-vendor lists, which block a vendor's telemetry hosts and keep the hosts its devices need: Samsung, LG webOS, Roku, Amazon, Apple, Windows and Office, TikTok, Xiaomi. Tick the kinds you own. IPv6 for the house, PPPoE and a static address come later.

### 🔒 Security & Fixes

- **The network follows an update** — An update restarts only the web UI; DNS, DHCP, blocking and the router keep running off the files already in place. So a fix to how one of those is set up used to wait until you saved its page again. System Update now makes each network config again and puts in place only what differs (Unbound's config, the blocklists, dnsmasq, radvd, the router's rules), saying what it applied in the update's log. Nothing happens while DNS is off, and an update that changes nothing touches nothing.
- **Router mode's NAT rules no longer pile up** — Every save in router mode (a forward, the DNS switch, now an address change) reloaded the firewall, and each reload added another copy of the NAT rules, because UFW re-reads its rules file without clearing the NAT table. The copies were identical until the NAS's address changed; then an old copy kept redirecting devices' DNS to the address the NAS no longer had, and turning router mode off left the rules in place until a reboot. The rules now live in chains of their own that are emptied and refilled each time, and the way back removes them; a NAS that already has old copies is cleaned up on its next save.

### 🔒 Security & Fixes

- **Greyhole starts when it's installed** — The setup wizard's install ended with Greyhole enabled for the next boot but not running, so files waited until a restart. Turning a service on now enables it, then starts it, as two steps: `systemctl enable --now` starts nothing for a service with only an init script, which is all Greyhole's package has. Turning one off stops it the same way.
- **The setup wizard's drives, copies and name, done the app's way** — The drives the wizard pools join the pool the way Disks → Greyhole Pool adds one, so going Back after installing Greyhole also updates its configuration and starts it. The copies chosen when installing Greyhole are kept only once it's installed, and become the default for new pooled shares everywhere (the Shares page used 2 regardless); the first share is pooled only when Greyhole is installed, and its folder is where the Shares page would put it. A drive shared as it is (NTFS, exFAT) shows on the summary. Renaming the server reaches Samba at once, and the helper names the new hostname in `/etc/hosts`: without that, every `sudo`, the app's own included, waited on DNS and warned "unable to resolve host". A browser test now walks the whole wizard, Greyhole's install included.
- **The install window in the app's look** — The window every install, update and audit streams into (System Update, apps, Greyhole, ZFS, Tailscale, the Cloudflare Tunnel, the security audit, System Dependencies and the setup wizard) is one of the app's glass panels now, instead of a navy terminal with pretend window buttons. Its title bar has a pill saying how the job is going (Running, with a pulsing dot, then Done, Failed or Waiting), steps and results are mint, problems red or amber, and Close and Continue are the app's buttons.
- **The sign-in page in the app's look** — The last page with the old teal style: the name and its wave mark above one glass panel, labelled fields, the mint button, and messages in the app's colours. After a wrong password the form keeps the name you typed and your Remember me choice, so only the password goes in again.
- **The setup wizard in the app's look** — Near-black glass over the water, mint, Space Grotesk and the app's buttons, the same as every page after it, and dark on every computer (it went light grey, with labels hard to read, on a computer set to light mode). A bar shows the step (Step 3 of 7). The install and preview windows cover the screen again instead of only the panel. A refused password no longer shows its message again on the next page, a share name that's taken or too short says so instead of failing with an error page, and the wording points to where things are now (Disks → Devices, Disks → Greyhole Pool), with what to do next at the end.
- **A fresh install, checked on a new Ubuntu 24.04 VM** — The installer shows the admin's first password as soon as it's made, not only at the end, so a later failed step can't lose it. It writes Samba's configuration the way System Update does, answering on your LAN only, without Ubuntu's printer shares. It no longer stalls for 90 seconds on a VM whose guest agent option is off (it says where to turn it on). It finishes by restarting Amahi-kai and checking that it answers. Running it again keeps your server's address and your choice of automatic updates, and restarts the app on the new code.
- **Installing from a checkout keeps its git history**, so System Update, the check for updates and the version shown work from the start. The one-line install takes options (`curl … | sudo bash -s -- --headless`), and `AMAHI_BRANCH=dev` installs the code in development for testing. `--with-greyhole` is gone: it left Greyhole half set up, and the setup wizard or Disks → Greyhole Pool installs it properly.
- **Ubuntu 24.04 only** — Debian was listed but never worked (the Docker and Tailscale repositories are Ubuntu's), so the docs no longer claim it, and the installer uses Ubuntu's Ruby 3.2 instead of building one. Amahi-kai's own service and the file search index's timer now come from `config/systemd`, so System Update keeps them current like the others.
- **The local domain is `home.arpa`** — New installs were given `amahi.net`, the old Amahi project's real domain, so the server's DNS would answer for it on your LAN. Installs that have it move to `home.arpa`, the name kept for home networks; any other domain stays.
- **SMART monitoring runs in a virtual machine** — Ubuntu's smartmontools service never starts in a VM, so on a NAS running in Proxmox with the drive controller passed through, smartd stayed off with real drives to watch. Amahi-kai now clears that condition at install and at every System Update, and starts it. With only virtual disks, smartd still finds nothing to watch and stops itself, shown as idle.
- **Unmounting a drive no longer blames system services** — Unmount, Preview and Format refused every mounted drive, saying it was in use by systemd-resolve, systemd-logind, mariadbd and other services. Those services run in a sandbox with their own copy of the mounts, but their copy follows the system's and goes away with it, so they never held the drive. Only an app's container, whose mounts are its own, is named now.
- **A ZFS pool an app still uses says so** — Taking a pool offline or deleting it while an app's container had one of its folders mounted (a share given to the app and deleted since) unmounted the pool, then failed with ZFS's "pool is busy", leaving it half offline. It's now refused before anything is unmounted, naming the app to stop first.
- **A share given to an app can't be deleted** — Deleting it left the app with the share's folder mounted, and a ZFS pool under it couldn't be taken offline. It's refused now, naming the app: take the share off with Change under the app's shares on Apps first.
- **Where to write** — The README, the website and the wiki's Getting help give an email for questions, catdogbark@pm.me, beside GitHub Issues.
- **Apps can keep their data on a ZFS pool** — An app's catalog entry can mark folders as `kind: dataset` (catalog format 3): the data that grows, like bitShare's files. Installing such an app asks for the ZFS pool under **Storage** (it can't be installed before there's a pool), and its data goes in a dataset of its own, `<pool>/apps/<app>`, covered by the pool's snapshots; its settings stay on the system disk. The app's row says which pool, and the pool's card lists the apps on it. A pool can't be taken offline or deleted while an installed app keeps its data there, and rolling it back stops those apps while it runs, then starts them again. Updates snapshot the dataset instead of copying it, and Undo update rolls back to the snapshot. Uninstall keeps the dataset unless its data is deleted.
- **A warning when the system disk runs low** — Files written to a Greyhole share land in its folder on the system disk before Greyhole moves them to the pool drives, and Amahi-kai, its database and its apps live there too, so a full system disk stops all of them. The dashboard and the Disks pages now warn when it has less than 10 GB free, and more urgently under 2 GB. Its free space is read when the page loads, not at the 15-minute health check.
- **A share stays where it was made** — A share's Folder (on Setup → Shares, under Storage) could be changed by clicking it and typing a path. That didn't move anything: the share then showed an empty folder while its files stayed in the old one, a pooled share left its links to its files behind, and a path on a Greyhole drive could be the very folder Greyhole keeps that share's copies in. The Folder now only shows where the share is, and the server no longer takes a new one. To move a share, make a new one where you want it and copy the files across.
- **Erase a drive's old ZFS label** — A drive replaced out of a ZFS pool keeps a ZFS label from no pool, and so does one from a pool on another server. Share storage never takes a drive with a ZFS label, so getting it back took `zpool labelclear` over SSH. Disks → ZFS Pools now has **Erase** on such a drive (it asks first), and says when a drive was replaced out of one of this server's pools instead of calling that pool "not on this server".
- **A pool's warning says what to click** — When a drive drops out of a ZFS pool, the warning at the top of the page and the pool's card passed on ZFS's advice, which named `zpool` commands. They now name the drive and say what to do on Disks → ZFS Pools: click **Bring online** if it's connected again, or connect it again (and click Bring online, or restart the NAS if it was already missing when the NAS started) or **Replace** it with a free drive.
- **Bring a pool's drive back online** — (Its first version failed with "cannot relabel … unable to read disk capacity": with autoexpand on, `zpool online` reads the disk's size, and it was given the drive's partition; it's given the disk now.) When ZFS takes a drive out of a pool (it went missing for a moment: a loose cable, a drive pulled and put back) it stays out once the drive is connected again, and getting it back took `zpool online` over SSH. Disks → ZFS Pools offers **Bring online** on that drive's row once its disk is there again; ZFS takes it back and copies what changed while it was out. Replace stays for a drive that's really gone.
- **A pool's snapshot setting says what it keeps** — "Keep 24 hourly and 30 daily" read like 24 snapshots an hour. It says "Keep the newest 24 hourly and 30 daily snapshots" now, with what that means beneath: one an hour and one a day, so any hour of the last 24 hours and any day of the last 30 days, each using space only for what changed since.
- **Fixed: Power off and Reboot didn't ask first** — Settings' Power off and Reboot, and Restart and Stop on Settings → Servers, asked through inline scripts, which the Content-Security-Policy refuses since it's enforced: one click powered off, rebooted or stopped with no question. They ask again (through the page's own script), and a spec now fails on any inline event handler in a template.
- **Settings → Jobs and Servers in a narrower window** — The job or service name and its line were squeezed to a word a line while the times beside them kept their room; they keep a readable width now.
- **ZFS's memory cache cap follows the NAS's memory** — The cap (2 GB, or half the memory on a smaller NAS) was worked out only when ZFS was installed, so memory added since wasn't counted: on the test VM, grown from 4 to 8 GB, it stayed at half of 4 GB. System Update works it out again when ZFS is installed.
- **Fixed: a ZFS pool couldn't be taken offline while a computer had its files open** — Taking a pool offline, or deleting it, unmounts it, which ZFS refuses while anything has a file or folder open there; with a computer connected over SMB, the page showed zpool's "pool or dataset is busy". Those SMB sessions are ended first now (the computers reconnect to the other shares by themselves), and the confirmations say so; anything else holding the pool is named instead, and the pool stays as it is.
- **Shares on ZFS pools** — A share can now live on a ZFS pool: choose the pool under the new **Where** in Create a New Share (System disk, the Greyhole pool once it has drives, or each ZFS pool). Its folder is in the pool's `shares` dataset (`/srv/pools/<pool>/shares/<name>`), made the first time a share goes there; ZFS keeps it safe with the pool's redundancy and snapshots, so it has no Greyhole copies, and it stays on its pool. The Shares list shows where each share lives (System disk, Greyhole · 2 copies, ZFS · <pool>), as do the file browser's cards; a pool's card lists its shares, and a pool with shares on it can't be taken offline or deleted. bitShare's data stays separate, never an SMB share.
- **Disks → Storage Pool is now Disks → Greyhole Pool** — Beside ZFS Pools, "Storage Pool" didn't say which pool it was. The tab, the dashboard's card, the share card's link, the setup wizard and the messages that point there say Greyhole Pool now (its address stays `/disks/storage_pool`).
- **Fixed: Disks → ZFS Pools' layout** — The page's introduction was cut off at the top (it sat inside the rounded panel, whose corner clipped it); it's above the panel now. A pool's buttons no longer squeeze their words onto two lines in a narrower window: they wrap below the pool's name. And the drives table keeps the card's side padding, so its first column and the Replace buttons line up with the rest of the card.
- **Guests can't sign in to the web UI** — A guest account is for the network shares (SMB) only, but it could sign in and see the dashboard, with the running apps, the server's stats and its drives. Its sign-in is refused now ("Guest accounts use the network shares (SMB) only", shown only once the password is right), and the session of an account made a guest after signing in ends. And someone signed in who isn't an admin, opening an admin page, is sent to the dashboard ("That page is for admins.") instead of the sign-in page.
- **Fixed: deleting a user who was connected left their account behind** — With the user connected over SMB, the system refuses to delete an account in use, and Amahi-kai deleted the web user anyway: the user vanished from the list, the account stayed, and its login couldn't be used again ("Login already exists in system"). Deleting a user now ends their SMB sessions first, and if the account still can't go, the user stays on the list and the page says why.
- **No more private home folders** — Samba's `[homes]` share is gone: it gave each user a private folder in their home on the system disk, with no pool copies, snapshots or size limit, and showed a `nobody` folder when browsing anonymously. New accounts get no home folder, and deleting a user removes one an older version made. A better way to do private folders is on the roadmap. Users keep their files in shares.
- **Fixed: reloading a page that answered a form asked to send it again** — A form the server refuses (a New User with no full name, a wrong password at sign-in) comes back as the same page with the reasons, and reloading that page, by hand or with System Update's Reload page, had Firefox ask whether to resend the form. Those pages now ask for themselves again when reloaded, on every layout (the main pages, sign-in and setup).
- **A user's card, redone like a share's** — Setup → Users: a user's card is in sections now, Account (full name, role, last sign-in) and Password, each setting with a line saying what it does, and Delete at the bottom saying what it removes (the account, its network share password and its home folder; shares stay). Change password is a button instead of a lock icon, an admin's card says why it has no Delete, and a role change swaps the two at once. The list's full names line up under their heading.
- **Fixed: a refused New User, Share, Host or DNS alias said nothing** — When the server turned one down (a user with no full name, say), the page came back with the form closed, so its reasons never showed and it looked as if nothing had happened. The form now opens with the reasons and what was typed (never the passwords), and the New User form marks what it needs: the username, the full name, and passwords of at least 8 characters.
- **A pool drive missing at boot no longer keeps apps from starting, or gets files on the system disk** — An app given a pooled share mounts the share's folder on each pool drive, and with one drive missing at boot its container couldn't start, and stayed stopped once the drive was back. Each time Docker starts, and when a pool drive is mounted again, the apps whose mounts don't match the pool are made again with the drives there are (the root helper's `apps.follow_pool`, which pool changes now use too, so an app whose mounts already match doesn't restart). And a data drive's empty mount point is made immutable while nothing is mounted on it (when it's mounted, and at System Update for a drive missing then, removing the empty metadata backup folder Greyhole's job remakes there every minute): with storage-2 missing, Greyhole had made that folder in `/mnt/storage-2`, on the system disk.
- **Fixed: a drive just taken out of the pool still couldn't be previewed** — The apps given pooled shares let go of a drive when Amahi-kai notices Greyhole has finished removing it, which only the Storage Pool and Shares pages did; going straight to Devices to unmount and preview it, the app still held it. Devices, and its Format, Mount, Unmount and Preview, notice it first now. And when an app's container does still have a drive mounted, Unmount, Preview and Format say which app, instead of failing with mount's "already mounted or mount point busy".
- **Apps follow the storage pool** — An app given a pooled share reads it through its container's mounts: the share's folder and its copy folder on each pool drive, made when the container was. After the pool changed, those went stale: a share turned Off and back on left the app pointing at folders Greyhole had deleted, a drive added later wasn't there at all, and a drive taken out of the pool stayed in use inside the app, so Disks → Devices couldn't preview it. Now, when a drive joins or leaves the pool or a share is pooled or turned Off, the apps given those shares are installed again with the same shares and version (each restarts for a few seconds; a stopped one stays stopped), and a pool drive with no folder for the share yet gets one, so the app sees the copies Greyhole makes there.
- **Fixed: a share's pool copies buttons sent two changes per click** — After the first change, − and + each sent the copies they'd been drawn with as well as the new value, at the same moment: going from 2 to 1 asked about turning the pool off, and the two changes raced (one turning the share off while the other set a copy). Each click sends one change now, and both buttons wait for its answer. A share that's turning off keeps its card open when the page reloads to show it, and the page checks every 10 seconds instead of 30.
- **Switches show what's saved after a reload** — Firefox puts a checkbox back the way it was when a page reloads, so a switch that saves as it's clicked could show the opposite of what's saved: after a drive left the pool, its In Pool box came back ticked beside "Add to pool". The In Pool boxes, a share's switches (Visible, All users, Writeable, each user's access and write, guests), Advanced, Docker and Network's DHCP switch now always show the server's value. A drive being removed from the pool is checked every 10 seconds instead of 30, so the page shows it gone sooner.
- **A drive added to the pool gets its copies now** — Adding a drive to Greyhole's pool, or raising a share's copies, has Greyhole check the pool straight away, so the copies the shares are short of are made within minutes. Greyhole's own daily check runs only after its configuration changes, the next morning: until then, a drive taken out and put back held no copies Greyhole counted. Disks → Storage Pool also reloads after a drive goes in or out with In Pool, so the drives and the pool's space are current; only a slow removal used to.
- **Fixed: the header in a medium-width window** — Between a phone's width and a wide window, the header no longer squeezes Amahi-kai onto two lines or pushes its buttons past the window's edge: the search moves to a row of its own below.
- **Fixed: deleting a pooled share left its files behind as links** — Deleting a share keeps its files (only an empty folder goes), but a pooled share's are on the pool drives: its folder kept links to them, and Greyhole no longer looked after them. Delete now waits until a share's files are back in its folder: turn its pool copies Off first, and the page says so. Either opens a **What's new** window: the changelog entries the update brings, its pull requests, and **Update now** or **Later**. With nothing new, it shows when Amahi-kai last checked, with **Check now** and **Repair**. The header button no longer starts an update straight after a "Run system update now?" prompt.
- **The root helper recognises the system disk again.** It read `lsblk`'s device list as a tree, but `lsblk` only nests partitions and volumes under their disk when its NAME column comes first, so every disk looked empty to the helper: its own check that a drive isn't the one the system runs from didn't hold, and Disks → ZFS Pools listed the system disk as free. The web app's separate check (the OS Disk badge and buttons on Devices) always held. Both now read a real tree and refuse a flat list, and specs check the test machine's real `lsblk`. What's new no longer shows a stray dash before each entry.
- **The services lists show ZFS's event daemon, SMART monitoring (smartd), Fail2ban and the VM guest agent** when they're installed (dashboard, System Status, Settings → Servers), each with what manages it. Drives without SMART data say why instead of a dash: a virtual disk (QEMU, VirtualBox, VMware, Hyper-V, virtio), a drive that gives none, smartmontools not installed, or not checked yet; Devices marks virtual disks.
- **Scheduled jobs on the dashboard and in Settings → Jobs.** The storage health check, the file search index, the check for updates, Ubuntu's automatic security updates and its monthly pool scrub, each with when it last ran, how that went and when it runs next (read from systemd; the scrub from the pools). The dashboard's System, Services and Jobs cards share one row. SMART monitoring shows as **Idle**, with why, when no drive has SMART to watch: smartd stops itself then (on a VM's virtual disks), which looked like a stopped service.
- **Tooltips show quickly and can be found.** They were the browser's own, which waits about a second and looks like plain text (the text cursor, nothing to say it's there), and don't work on touch screens. They're now Bootstrap's, after 150 ms, on hover or keyboard focus. Extra information is marked: an ⓘ on badges such as Idle, a dotted underline and the help cursor on times and versions. Icon buttons (the header's, the file browser's) name themselves the same way. What you need to know is on the page instead: why a service is idle, a drive's SMART details on Devices.
- **System Update no longer says an update failed when it worked.** Stopping Amahi-kai for the restart also stops the update window's check on the update job, and a check stopped halfway read as "the update is over": the window showed "✗ The update didn't finish" while the update went on to finish fine. A check with no answer now counts as still running, and the window always waits for the restarted version to say how the update ended. The update that installs this runs the old window, so it can still show the false message once.
- **The web file browser only views and downloads.** Upload, new folder, rename and delete are gone: files change over the network shares (SMB), so Samba, each user's share permissions and Greyhole on pooled shares see every change, and a stolen web login can't change files. (Changes made in the browser went around Greyhole: an upload got no extra copies, and a delete left the copies behind.) Files in pooled shares now preview and download (they're links to a pool drive, which the browser refused). **Download as zip** works: the gem it needs was missing, so it always failed. A zip is now written a piece at a time instead of reading each file into memory, and only includes files that are in the share.

- **Small fixes before Phase 4:**
  - The login throttle counts attempts by the real client address. A LAN client could send a made-up `X-Forwarded-For` on every attempt and never be throttled; visitors through the Cloudflare Tunnel are counted by the address Cloudflare reports.
  - Static DHCP hosts (Network → Hosts) reach dnsmasq: each gets a `dhcp-host` line, and adding, changing or removing one rewrites the config. They were saved but had no effect.
  - The Gateway page remembers its DHCP and DNS checkboxes after saving.
  - Re-running the setup wizard's storage step keeps the drives already in the pool instead of emptying the list.
  - Adding a user through a JSON request no longer fails with a server error, and the Apps page still loads when checking Docker fails.

### 🔧 Architecture & Code Quality

- **No inline scripts** — The JavaScript that eight pages carried in their own `<script>` blocks (the install window, the security audit, Remote Access, the setup wizard's drives and Greyhole steps, the Docker switch, the setup layout's messages) lives in files now, with the pages' addresses passed in from their buttons. Step two of three towards a Content-Security-Policy that refuses inline scripts.
- **No inline event handlers** — Every button, link and form that ran a snippet of JavaScript from its own markup (52 of them, on 20 pages) now says what it does in its attributes, and one small script does the calling. It's the first of three steps to a Content-Security-Policy that refuses inline scripts, which stops a script smuggled into a page from acting as you. Nothing changes in what the buttons do; the dashboard's tiles light up on hover by stylesheet now.
- **Three small cleanups from the roadmap** — A share's toggles (All users, Visible, Writeable, guests, each person's access, Clear the list) have one set of rules, in `ShareAccessManager`; the Shares page's actions call them instead of repeating them. Advanced mode is read once per page, and only on pages that show it, instead of on every request (and twice on some). The dashboard and System Status read the OS name, load and memory through `SystemInfo`, the same way, instead of each in its own way.
- **The last leftovers** — A final sweep for code nothing uses:
  - **Gone:** an empty search page with no route, two unused methods, two scripts nothing loaded (one only comments), Turbo's copy (189 KB, unused since Turbo went), the `stimulus-rails` gem (Stimulus is bundled with Amahi-kai), six unused translations, an old DHCP-lease reader from the ISC DHCP days, and a lease filter that would have crashed if anything had called it.
  - **Browser search:** the original Amahi's "add as a search engine" file went to an address that doesn't exist (`http://hda/...`); it and its link on every page are gone.
  - **Tidier code:** helper methods that were meant to be private are now, and two controller methods Rails treated as actions on every page aren't. Settings had three ways to read a value; there's one.
  - **CI:** RuboCop's list of old offenses is empty, so it's gone and any offense fails. Every spec runs; the filters for specs CI skipped had nothing left to skip.

- **The last of the old command runner goes** — With everything that changes the system going through the root helper, and everything that reads it running as argument lists, the old way of running command strings (with its log masking and its error type) had nothing left to run. It's gone, with 13 places that still caught its error, and the cloudflared check runs the same way as the rest.

- **More dead code out** — Nothing in the app used these either:
  - **Settings and platform leftovers:** the settings file nothing read (`config/yetting.yml`, with its loader), and the platform's service names and file paths for Apache, monit and the DHCP server.
  - **Unused methods:** on shares (the old default shares, the Samba domain name), users (share write checks), settings and DNS, two do-nothing steps on every request, and a few helpers.
  - **Pages and styles:** three page templates nothing showed (DNS aliases' old page, a user settings page and a full-screen layout), Rails' generator templates, the drive table's old stylesheet and a few unused styles.
- **Tests CI skipped now run** — Search's share indexing, the Apps page's requests and the storage pool's requests were marked as needing a real NAS, so CI never ran them. They don't need one, so CI runs them now.

- **Share tags' column goes** — The last of tags: their database column is dropped.

- **Users' old SSH-key column goes** — Amahi-kai stopped saving and installing users' SSH keys long ago (web users get no shell), so the database column that held them is dropped.

- **The themes table goes** — With the theme system gone (#102), its database table and its setting are dropped. The last code that still wrote share tags is gone too, so their column can be dropped in the next update.

- **Dead code out** — Nothing in the app called these, so they go:
  - **A leftover pool toggle (the one that mattered):** an old share-side "toggle disk pool partition" took a drive's record out of the pool directly, skipping the safe removal that moves its files first. An old share copies toggle likewise bypassed turning a share Off safely.
  - **Unused routes and actions:** an any-setting toggle, the old one-shot installs of dnsmasq, Greyhole and apps (their install windows replaced them), the old tunnel set-up and cloudflared install, app restart and status, the generated routes for user and share pages that don't exist, and a page with no view at all (`/shares/disk_pooling`).
  - **Tags:** their code (the database column goes in a later update).
  - **Unused translations:** 293 of the 453 English strings.
- **Missing labels filled in** — A spec now fails if a page asks for a translation that isn't there. That turned up labels that had never existed, which those pages showed as stand-in text:
  - **Hosts:** the hosts page's headings, button, form and remove prompt.
  - **DNS aliases:** the page's form, and its remove prompt.
  - **Network settings:** the DNS servers fields and button, the DHCP range's "Starts at" and "Ends at", and the lease time.
  - **Elsewhere:** the DNS provider list's Cloudflare entry (the default), and search's Previous page link.

- **The disk code in one place, and no commands through a shell** — Drives, their temperatures, what's mounted and the drives Greyhole can pool are read by one library instead of three. Every command Amahi-kai runs to read the system now runs as an argument list, without a shell: package and service checks, the dashboard's and System Status's figures, the drive preview's folder sizes, a share's size and Samba's network checks. The hostname, kernel, cores, uptime and swap are read directly, with no command at all. (The debug pages keep theirs until they're rebuilt in Settings.)
  - **Fixed:** Disks → Storage Pool's Available Partitions shows the partition itself (`/dev/sdb1`, where it showed the drive, `/dev/sdb`, and an NVMe partition as `/dev/nvme`), and lists only drives mounted under `/mnt`, the only ones Greyhole's pool can take.
  - **Settings → Details** shows the uptime as the dashboard does ("up 3 days, 4 hours") instead of the raw `uptime` line.

- **Lighter: only the parts of Rails it uses, and no Turbo** — Amahi-kai loaded all of Rails, including mail, file attachments, rich text, inbound email and websockets, none of which it uses. Now it loads only the parts it does use. It also loaded Turbo, then switched it off on every page. Booted for production, the app takes about 93 MB instead of about 112 MB (18 MB, or 16%, less per app process), and loads 357 fewer files.

- **One look, no themes** — With every page dark and one look, the theme system goes. That's the Settings → Themes page, the second "vertical" theme, the loader that read each theme's `init.rb` on every request, the light theme's colours, the old theme switcher's styles, and the theme's out-of-date Sass. The look is `app/assets/stylesheets/theme.css`, joined last into the one stylesheet every page loads, and it's about a third shorter. Search results use the file browser's icons, so the old set of PNG file icons is gone, as are a few unused helpers and icons.

- **Drive removal's database change is safe to rerun** — If a System Update stops partway and runs again, adding the Removing column to the pool drives' table no longer fails because the column is already there.

- **Addresses in one place** — Every address of Amahi-kai or one of its apps is made in one place (a spec checks), so HTTPS can be added later as an optional front door without hunting through the code; plain HTTP stays fully working. Remote Access shows the Tailscale address that way too.

- **Dummy mode is gone.** It was a developer switch that made Amahi-kai skip every change to the system, and a setting in `amahi.env` (`AMAHI_DUMMY_MODE`) could turn it on, even on a real NAS, where every button would then silently do nothing. Now there's a fixed rule with no setting: outside production (development and the tests) system commands and the root helper are only recorded; production always runs them. The Dummy Mode row on System Status is gone, and the installer no longer writes the setting (an old line in `amahi.env` is ignored).
- **No Sass compiler any more.** The stylesheets are plain CSS, and Bootstrap is its official 5.3.8 build (CSS and JavaScript), so System Update no longer compiles LibSass, which is unmaintained, and builds assets faster. Pages look exactly as before (compared screenshot by screenshot). The `sassc`, `sass-rails` and `bootstrap` gems are gone. Theme sources are rebuilt by hand with Dart Sass (`public/themes/README.md`).
- **System Status shows the deployed commit** in its Amahi-kai row (it showed the word "amahi-kai"). The update window no longer lists every gem and every compiled asset file.
- **Plugin Consolidation** — All 6 plugin engines (Users, Shares, Network, Disks, Apps, Settings) merged into main app. Single layout, unified routing.
- **Auth Modernization** — Authlogic → `has_secure_password` (bcrypt). Removed DES crypt (was truncating to 8 chars!). Linux users created with a locked password. Two stores: bcrypt (web) + pdbedit (Samba).
- **Login Rate Limiting** — rack-attack throttling on login attempts.
- **12 Service Objects** — SetupService, DiskService, FileBrowserService, ContainerService, CloudflareService, DockerService, TailscaleService, ShareAccessManager, ShareFileSystem, SambaService, DnsmasqService, SwapService.
- **Security Hardening** — SQL injection, shell injection, XSS, CSRF protection. CSP headers. Narrowed rescue clauses from `StandardError` to specific exceptions.

- **Icon System** — 34 vendored Lucide SVGs via `IconHelper`. Zero glyphicons/bootstrap-icons remaining.

- **Removed code the app no longer uses.** Samba's NT4 domain-controller (PDC) mode, which nothing could switch on, and printer sharing: smb.conf now turns printing off instead of pointing at CUPS, which the NAS doesn't run.
